Workflow v5 — practice extraction from the PAD

Reading units · extract → judge → expand context · one row per practice. Designed to be tuned on a few projects before scaling up.

1. Definitions

Approach
A specific, identifiable practice: a concrete thing the project does, named precisely enough that the same practice could be recognised in another project. It must be related to digital technology, data or AI, and it maps to exactly one category of the working paper Innovation Patterns in the World Bank Group Portfolio: Operational, Technological, Financial or Collaborative.
Specificity test
The practice names (1) the mechanism, tool or system and (2) what it is used for / who uses it. "Use of technology", "digital transformation" or a technology name alone fail the test and are not extracted.
Adoption
apply — this project finances, builds, deploys, requires or has implemented the practice; prospect — envisaged for the future without commitment; discuss — discussed as background, lessons or options. Only apply counts in headline figures.
Reading unit
The smallest piece of text read at once: one numbered paragraph of the PAD (the running paragraph numbers are followed), or, where numbering cannot be followed, a window of consecutive sentences of about 1,200 characters. Units never split a sentence and keep character offsets into the source file. Half a page ≈ 1,600 characters.

2. Steps

  1. Locate PAD (Python) — the newest PAD of the project; fallback Project Paper → Program Document → PID. No document: the project is marked failed / Unclear.
  2. Reading units (Python) — the document is segmented into sentences with offsets, then grouped into units (units.target_chars / max_chars / min_chars).
  3. Cue filter (Python) — units that carry a digital / data / AI keyword cue (DDAT keyword lists + enabling-technology terms of the innovation dictionary); boilerplate units dropped; at most max_units_per_project units, ranked by cue density.
  4. Extract practices (LLM, 01_extract) — ten units per call. For each unit the model returns zero or more practices with category, adoption, a one-sentence description and 1–3 sentence ids. Sentences are resolved in Python, so evidence is verbatim and anchored by construction; an unresolvable id drops the practice.
  5. Judge / expand (LLM, 02_validate, 03_revalidate) — every practice is judged on four questions (specific? digital? right category? evidence and adoption supported?) with verdict accept / revise (corrected wording, category or adoption) / expand / reject. For expand, the unit is widened by validate.expand_chars (≈ half a page) on each side and judged again, this time to a final verdict. Rejected practices are written to the exclusion log with the judge's reason.
  6. Sector & theme (LLM, 04_codes) — one sector and one theme per accepted practice, chosen from the project's own projects.csv lists (assigned directly when the project has a single option).
  7. Merge duplicates (LLM, 05_merge, one call) — practices that describe the same mechanism for the same purpose are grouped; their evidence is pooled.
  8. Build records (Python) — one approach per group: name = practice, adoption = highest among members (apply > prospect > discuss), number_of_evidence = pooled evidence sentences; one evidence row per sentence with unit id, paragraph number, judge rounds and verdict.
  9. Replication scan (Python) — explicit P-code references and TF-IDF similarity against the portfolio store (unchanged from v2).

3. What to look at when tuning

  • Exclusion log (table 4 / "rejected" in the drawer): the judge's reasons show whether the extractor is too generous (many reject: generic) or the specificity rule is too strict.
  • judge_rounds on evidence rows: practices that needed the expanded context; a high share suggests larger units or a larger expand_chars.
  • Cue filter recall: units without a cue are never read; candidates.require_cue: false reads every non-boilerplate unit (more calls).
  • Merging: compare approaches before and after the merge step in the trace (merged).

4. Cost profile

Per project: ⌈candidate units / 10⌉ extraction calls + ⌈practices / 12⌉ judge calls (+ one more round for the expanded ones) + ⌈practices / 30⌉ coding calls + 1 merge call. A typical PAD (60–100 candidate units, 20–40 practices) is 20–30 calls of 3–6k input tokens; the system prompt is cached on Anthropic. Token counts and a list-price cost estimate are recorded per run (llm_usage) and printed by the CLI.
