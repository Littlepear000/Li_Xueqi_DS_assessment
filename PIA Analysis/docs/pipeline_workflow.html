PIA Analysis — Pipeline Workflow

Project Innovation Approach Analysis · Python package piaa · Draft v0.1 · 2026-11-05 · Status: skeleton, to be filled in step by step

How to read this document. It is the design map of the piaa package: what goes in, which stages the data passes through, which public functions ("APIs") each stage exposes, and how outputs are versioned. Items marked TBD are placeholders that will be filled in during the next design steps.

1. Design principles

PrincipleWhat it means in practice
Single input: the raw-data folderThe only required input is a folder (e.g. raw_data/) containing projects.csv — the list of projects in scope — and a documents/ sub-folder with local project documents. Nothing else is assumed.
project_id is the join keyEvery row in projects.csv, every local document file name, every API response and every output row is linked by the World Bank project ID (e.g. P176935).
User-specified output folderEvery run writes to an output_dir passed by the caller. The package never writes next to its own source code.
Never overwrite, always versionEach run creates a new, time-stamped run folder with a new copy of the Excel outputs. Previous versions stay untouched.
Check-before-recomputePer-project results are cached. On re-run the caller chooses to reuse cached results, refresh everything, or refresh only what is new or changed.
Single-record first, batch secondEvery analysis function can be run for one project_id so that it can be tested repeatedly before the full database is built.
Driven from a Jupyter NotebookThe package is installed locally (pip install -e) and called from a notebook template that lives in the user's project folder.
English onlyAll code, comments, docstrings and documents inside PIA Analysis/ are in English.

2. End-to-end flow

Stage 0

Inputs

  • raw_data/projects.csv — list of projects in scope
  • raw_data/documents/*.txt — local project documents
  • output_dir chosen by the user
  • Run options (reuse / refresh)
Stage 1

Catalog & Acquisition

  • Load and validate projects.csv
  • Check every project against the WB Projects API
  • List documents available per project in the WB Documents API
  • Audit local vs. online documents; download what is missing
  • (Future) expand the project catalog from the API
Stage 2

Project Analysis

  • Build one bundle per project (CSV row + documents)
  • Run the Project Flow on one project → one record
  • Single-record test API for repeated manual checks
  • Batch analysis with cache
Stage 3

Database Build

  • Assemble per-project records into two tables
  • Write Table 1 and Table 2 as Excel
  • Write a run manifest (inputs, options, versions)
  • Accessor APIs to load either table
Stage 4

Consumption

  • Jupyter Notebook template calls the package
  • Versioned Excel files in output_dir
  • Re-run on CSV / document updates
Cross-cutting: run registry & cache. Every stage records what it did under output_dir/. Per-project results are fingerprinted (project row + document set) so that unchanged projects can be skipped on later runs.

3. Inputs in detail

3.1 projects.csv

One row per project in scope. Current columns:

project_id, project_name, country, region, vertical, lead_practice, status,
approval_date, commitment_usd, sector_names, sector_percents, themes

The file can be updated at any time (rows added, removed or edited). It is the sole definition of "which projects are in scope".

3.2 documents/

Plain-text documents, one file each, named by convention:

{project_id}_{doc_type}_{doc_date}_{guid}.txt
e.g. P158418_PAD_2018-12-21_443201548471646286.txt

The trailing guid equals the document ID in the World Bank Documents & Reports API, which makes local files and online records directly comparable. Known document types so far: PAD, PID, ISR, ProjectPaper; others may be added. TBD: final list of document types used by the analysis

3.3 External sources (World Bank APIs)

APIEndpointUsed for
Projects APIhttps://search.worldbank.org/api/v2/projectsVerify a project ID exists; pull project metadata; (future) list candidate projects by fiscal year / filters.
Documents & Reports APIhttps://search.worldbank.org/api/v3/wdsList documents per proid; filter by docty_exact and date; download full text via txturl. Must paginate (rows/os); Additional Financing documents are filed under the parent project ID.

4. Public API catalog (by stage)

Function names below are the proposed public surface of piaa. Signatures are indicative and will be finalised stage by stage.

Stage 1 Catalog & Acquisition — module piaa.catalog / piaa.wb_api

1.1load_projects(raw_dir) → ProjectList
Purpose
Read projects.csv, validate required columns and ID format, de-duplicate, report problems.
Output
DataFrame + validation report (duplicates, malformed IDs, missing fields).
1.2check_projects_online(project_ids) → CoverageReport
Purpose
Query the Projects API for every ID; confirm it is found and return key metadata.
Output
Table: project_id, found_online, api_name, api_status, api_approval_fy, …
1.3list_online_documents(project_id, doc_types=None) → DocumentIndex
Purpose
List every document the Documents API holds for one project (paginated; parent-project handling for Additional Financing).
Output
Table: project_id, guid, doc_type, doc_date, txturl, pdfurl
1.4audit_documents(raw_dir, project_ids=None) → AuditReport
Purpose
Compare local documents/ against the online index: which projects have no local documents, which document types are missing, which local files do not match any online record.
Output
Gap table per project + summary counts.
1.5fetch_documents(project_ids, doc_types, dest_dir, overwrite=False) → FetchLog
Purpose
Download full text for missing documents and save them with the standard file name convention so they become indistinguishable from pre-existing local documents.
Reference
Based on the earlier prototype _archive/…/api_probe/fetch_wb_documents_v0.py and API_NOTES.md.
1.6expand_catalog(filters) → CandidateProjects Future
Purpose
Pull additional candidate projects from the Projects API (by fiscal year, practice, theme, …) to help grow projects.csv.

Stage 2 Project Analysis — module piaa.analysis

2.1build_bundle(project_id, raw_dir) → ProjectBundle
Purpose
Collect everything known about one project: its CSV row, its local documents (parsed, typed, dated), and any API supplement.
2.2analyze_project(project_id, raw_dir, config=None) → ProjectRecord
Purpose
The single-record test API. Runs the full Project Flow on one project and returns the record that will later become one row in each output table, together with an explanation trace (which document / passage supported each field).
Project Flow
TBD: the sequence of analytical steps (document selection → extraction → classification of innovation approach → scoring) will be defined in the next design step.
2.3analyze_batch(project_ids, raw_dir, cache_dir, mode="reuse") → list[ProjectRecord]
Purpose
Run analyze_project over many projects with caching. mode: reuse (skip projects whose fingerprint is unchanged), refresh (recompute all), missing (only projects with no cached result).

Stage 3 Database Build — module piaa.database

3.1build_database(raw_dir, output_dir, mode="reuse", run_label=None) → RunResult
Purpose
The aggregate API. Executes Stage 1 checks → Stage 2 batch → writes both Excel tables and a run manifest into a new versioned run folder.
Output
Paths of table1, table2, run_manifest.json, plus counts (reused / recomputed / failed).
3.2load_table1(output_dir, run=None) · load_table2(output_dir, run=None)
Purpose
Load either output table from the latest run (default) or a named run as a DataFrame.
Schema
TBD: column definitions of Table 1 and Table 2
3.3list_runs(output_dir) → RunIndex
Purpose
Enumerate previous runs with their time stamp, label, input fingerprint and output files.

5. Output folder layout & versioning

{output_dir}/ ├── runs/ │ ├── 2026-11-05_2230_initial/ │ │ ├── table1_<name_tbd>.xlsx │ │ ├── table2_<name_tbd>.xlsx │ │ ├── run_manifest.json # inputs, options, package version, counts │ │ └── run_log.txt │ └── 2026-11-12_0910_csv_update/ │ └── … ├── cache/ │ ├── projects/{project_id}.json # per-project analysis record + fingerprint │ └── online_index/{project_id}.json └── latest → runs/2026-11-12_0910_csv_update (pointer file, not a symlink)
RuleBehaviour
New run folder every timeFolder name = timestamp + optional label. Existing run folders are never modified.
Fingerprint per projectHash of the project's CSV row + the set of (file name, size, mtime) of its documents. If unchanged and mode="reuse", the cached record is copied into the new run without recomputation.
ManifestRecords the projects.csv hash, the document count, the mode, the package version and per-project status (reused / recomputed / failed / no-documents).

6. Update scenarios

What changedWhat the pipeline does
Rows added to projects.csvNew IDs are checked online (1.2), their documents listed and fetched if absent (1.3–1.5), analysed (2.2), and appended; unchanged projects are reused.
Rows removed from projects.csvRemoved projects are excluded from the new run's tables; their cache entries are kept for traceability.
New local documents for an existing projectFingerprint changes → project is recomputed automatically even in reuse mode.
A project has no local documentsFlagged by the audit (1.4); fetch_documents (1.5) pulls them from the Documents API; if nothing exists online the project is marked no-documents in the manifest.
Analysis logic / config changedRun with mode="refresh" to recompute everything into a new run folder.

7. Jupyter Notebook template (planned)

A notebook piaa_analysis_template.ipynb will ship with the package and follow the same stage order:

import piaa

RAW_DIR    = "path/to/raw_data"
OUTPUT_DIR = "path/to/output"

# Stage 1 — catalog & acquisition
projects = piaa.load_projects(RAW_DIR)
coverage = piaa.check_projects_online(projects.ids)
audit    = piaa.audit_documents(RAW_DIR)
piaa.fetch_documents(audit.missing, dest_dir=f"{RAW_DIR}/documents")

# Stage 2 — single-record tests (repeat as needed)
rec = piaa.analyze_project("P176935", RAW_DIR)
rec.show()                      # record + explanation trace

# Stage 3 — build the database
run = piaa.build_database(RAW_DIR, OUTPUT_DIR, mode="reuse", run_label="initial")
t1  = piaa.load_table1(OUTPUT_DIR)
t2  = piaa.load_table2(OUTPUT_DIR)
